# What CloudGauge checks

The catalogue: every check and briefing, by report category, with its verdicts, what it reads and the fix line it carries. How a scan runs and how a category is scored: [architecture.md](architecture.md); the check names a dashboard or a script may depend on: [stability.md › Check names](stability.md#check-names).

In this page: [Security & Identity](#security--identity) · [Cost Optimization](#cost-optimization) · [Reliability & Resilience](#reliability--resilience) · [Operational Excellence & Observability](#operational-excellence--observability) · [AI-Powered Insights (Gemini)](#ai-powered-insights-gemini)

CloudGauge scans an organization, a folder or a project across several key domains, modeled after the Google Cloud Architecture Framework. Items marked *(organization scans)* describe the organization itself or query an organization-level API, so they run in an organization scan only; everything else runs in all three scopes, for the projects in scope.

## Security & Identity

* **Organization Policies**: Checks the organization policies of a best-practices table against the scope's *effective* policies: for a folder or project scan the check walks the hierarchy from the organization down to the scanned resource, the nearest policy winning (a folder's over the organization's, a project's over both). It runs even for a folder that holds no project. A boolean constraint is compliant when enforced as the table says; a **list constraint** *(v18)* when a policy configures it (denies all values, or names allowed or denied values) — `allValues: ALLOW` and `restoreDefault` do not count; a constraint the table says to leave unset ("won't have") passes when it is unset. A hierarchy level whose policies cannot be read is an *Error*, not a silent "Not Configured". The table itself ships inside the image, a `gs://` or `https://` URL replaces it, and an overrides file in the results bucket amends it constraint by constraint without a redeploy — the report says which table it was scored against *(v18.1; see [Customising the policy table](development.md#customising-the-policy-table))*.
* **Organization IAM** *(organization scans)*: **Critical Org-Level Roles** — who holds Owner, Organization Administrator, Editor, Billing Administrator, Security Administrator, Organization Role Administrator or Folder Administrator on the organization, by kind of principal *(v18)*: a group is the practice and makes a Compliant inventory; a person is *Investigation Recommended* (grant through a group); a service account, a consumer account, a whole domain or the public is **Action Required**. Google-managed service agents are not listed. **Public Org-Level Access** — `allUsers` or `allAuthenticatedUsers` on any role. Every row carries the `gcloud organizations remove-iam-policy-binding` line, with the binding's condition.
* **Primitive Roles (Owner or Editor)**: Every project's Owner and Editor holders by kind of principal *(v18)* — a user-managed service account, a consumer account, a whole domain or the public (`allUsers`/`allAuthenticatedUsers`, on any role) is **Action Required**; a person, a group or a default service account *Investigation Recommended* — read with policy version 3 so conditional grants show their condition. Google-managed service agents (the Google APIs service agent holds Editor in every project by design) are not counted, so a clean organization can pass. The fix line removes the binding; the IAM Least Privilege rows name the predefined role to grant first.
* **Security Command Center** *(organization scans)*: Reads the organization's **subscription tier** from the Security Command Center Settings API *(v18)*: Premium and Enterprise are Compliant; Standard is *Investigation Recommended* with a note on what the paid tiers add (a tier is a purchasing decision, not a misconfiguration); an organization that never activated Security Command Center is **Action Required**.
* **SA Key Rotation**: User-managed service account keys older than 90 days that can still authenticate *(v18)*: disabled keys, expired keys and the keys of disabled accounts are not counted (delete them). Each row names the key, its age, expiry and origin (created in Google Cloud or uploaded), with the `gcloud iam service-accounts keys disable` line. Since v18.7 the same listing writes **User-Managed Keys** (below): every account with a live key, whatever its age.
* **Public GCS Buckets**: Buckets whose IAM policy grants a role to `allUsers` or `allAuthenticatedUsers`, read together with **Public Access Prevention** *(v18)*: a binding PAP blocks — enforced on the bucket, or inherited from an enforced `storage.publicAccessPrevention` organization policy — is dormant and *Investigation Recommended* (remove it); one it does not block is **Action Required**, with the lines that remove the binding and enforce PAP. *(v19.3)* adds one Informational line per project counting the buckets that **rely on IAM alone** — not public today, Public Access Prevention enforced neither on the bucket nor by the organization policy, so nothing stops a public grant tomorrow.
* **Open Firewall Rules**: Enabled *ingress allow* rules from the internet (`0.0.0.0/0` or `::/0`) *(v18)*: what each opens (protocols and ports), to whom (target tags or service accounts, or every instance), its priority. A rule opening everything, a port range, or a port with its own Security Health Analytics detector (SSH, RDP, databases, caches, directory services, …) is **Action Required**; one opening only the web ports or ICMP *Investigation Recommended*. Deny rules — the hardening pattern — are never findings. The fix is the IAP TCP-forwarding range for SSH/RDP rules, narrower source ranges or deletion otherwise. Since v18.3 the **firewall policies** under the scope — hierarchical and network — are judged the same way, the policy named with where it is attached (a folder or project scan sees the policies under it, not those inherited from above).
* **Cloud SQL Security**: Three rules per instance *(v18)*: **TLS not enforced** (`sslMode` is `ALLOW_UNENCRYPTED_AND_ENCRYPTED`; `ENCRYPTED_ONLY`, the recommended mode, passes — the legacy rule read the deprecated `requireSsl` and flagged it), **Open to the internet** (an authorized network of `0.0.0.0/0` or `::/0` on a public IP), both **Action Required**; **Public IP** alone *Investigation Recommended*. Each row carries the `gcloud sql instances patch` line (a replica's names its primary). *(v19.3)* adds the instance-level **password policy** (none → *Investigation Recommended*) and the **server CA certificate's expiry** (*Investigation* under 90 days, **Action Required** under 30, with the create-and-rotate lines).
* **VPC Configuration**: A project's `default` VPC network — one **Action Required** row — or a **legacy** (subnet-less) network *(v18.3; CIS 3.2)*, with the auto-mode subnets that lack Private Google Access counted into it — and any other subnet without Private Google Access (*Investigation Recommended*, with its region and the `subnets update --enable-private-ip-google-access` line) *(v18.1)*. Proxy-only, Private Service Connect and NAT subnets cannot have it and are not judged, nor is the subnet GKE creates for a cluster's private control-plane endpoint; an IPv6-only subnet counts its IPv6 access. One aggregated listing per project.
* **GCS Uniform Bucket-Level Access**: Finds buckets without Uniform Bucket-Level Access (UBLA) enabled, with the `--uniform-bucket-level-access` line.
* **VM External IPs**: Instances that *hold* an external address — IPv4 or IPv6 — one row per instance with its zone, status, addresses and kind *(v18)*: a stopped instance whose ephemeral address was released is no longer a row; a GKE node is *Investigation Recommended* (the fix is a private node pool), a MIG member's fix is its template, a standalone instance's the `delete-access-config` line.
* **Advisory Notifications** *(briefing)*: Lists Google's Mandatory Service Announcements, Security & Privacy Advisories, Threat Horizons reports and sensitive-action digests for the scanned scope (the organization, or each project of a folder/project scan) from the last 365 days, one table with a `Type` column, affected resources and (for digests) the actions and actors. Always *Informational*: these are Google's messages, not the customer's posture.
* **Advisory Notifications Settings**: Flags a scope in which a notification type is turned off (*Action Required*), and reports when the scanner cannot read the notifications or the settings (*Error*; see the [prerequisites](operations.md#common-prerequisites-required-for-all-methods)).
* **IAM Least Privilege** *(v17)*: The IAM recommender's recommendations for the scanned organization or folder itself and for every project in scope — principals holding a role whose permissions they have not used in 90 days, with the role to replace it with (or *none (remove)*) and the `gcloud … remove-iam-policy-binding` / `add-iam-policy-binding` lines that apply it.
* **GKE Credential Exposure** *(v17.1)*: One row per node pool of every Standard cluster in scope that has something to say: whether its pods reach the **GCE metadata server** (the node's token and `kube-env` are one HTTP request away from any SSRF) or the **GKE metadata server** (Workload Identity Federation), the node service account (the Compute Engine default account is named as such), its project-, folder- and organization-level roles, its OAuth scopes, and the verdict in one sentence — *one SSRF from roles/editor on project X* is **Action Required**; GCE metadata with a least-privilege account, or GKE metadata with the default account, is *Investigation Recommended*. Fix lines: `--workload-pool`, `--workload-metadata=GKE_METADATA`, a new pool on a `roles/container.defaultNodeServiceAccount` account.
* **Service Account Impersonation** *(v17.1)*: Who can become which service account — `roles/iam.serviceAccountTokenCreator` and any role carrying `iam.serviceAccounts.getAccessToken`, `implicitDelegation` or `signBlob` (custom roles included), key creation, account administration, `actAs`, and Workload Identity bindings — with the **reach** of each grant: *every service account under projects/x (27)* for a project-, folder- or organization-level binding, *3 of 27 service accounts in projects/x* otherwise. Token minting granted resource-wide, account-to-account chains, public or domain principals, principals from outside the organization and Workload Identity for the `default` Kubernetes account are **Action Required**; a person's grant on one account is *Investigation Recommended* (your own operator's grant for `tools/iap_token.py` shows there). Google-managed service agents are not listed; primitive roles stay with Project IAM.
* **GKE Control Plane Exposure** *(v17.1)*: A public endpoint with authorized networks off, or with `0.0.0.0/0` among them (**Action Required**); authorized networks that admit every Google Cloud public IP, anonymous authentication and `system:authenticated`/`system:unauthenticated` bindings (*Investigation*); legacy ABAC, an issued client certificate, basic authentication (**Action Required**). Reads both the classic fields and `controlPlaneEndpointsConfig`.
* **GKE Node Hardening** *(v17.1, Investigation Recommended)*: Nodes with public IP addresses; no network policy enforcement (neither NetworkPolicy nor Dataplane V2, so pod egress to the metadata server cannot be blocked); Shielded nodes or Secure Boot off; a node image other than Container-Optimized OS; Binary Authorization off; the security posture dashboard or workload vulnerability scanning off; application-layer secrets encryption off; since v18.2, integrity monitoring off on a pool, intra-node visibility off (pod-to-pod traffic on one node invisible to flow logs and firewall rules), a routes-based (not VPC-native) cluster and an alpha cluster — the last two with no in-place fix. Autopilot manages its nodes, so only the cluster-level items apply to it.
* **GKE Threat Detection** *(v17.1)*: The Security Command Center settings' *effective* state per cluster — **Container Threat Detection** — and per project — **Event Threat Detection** — (**Action Required** when either is off; on the Standard tier both are unavailable); clusters that do not send `SYSTEM_COMPONENTS` and `WORKLOADS` logs, and projects without data-access audit logs for `container.googleapis.com` (*Investigation*): the evidence an incident response needs.
* **VPC Service Controls Coverage** *(v17.1, Investigation Recommended)*: From the organization's access policies (scoped policies included) — scanned projects outside every enforced perimeter, perimeters that leave the token-replay services unrestricted (`iamcredentials`, `storage`, `secretmanager`, `container`, `sqladmin`, `compute`), dry-run-only perimeters — or one row saying the organization has no perimeter at all. A perimeter stops a stolen token at Google's APIs from outside; it does not protect a Kubernetes API endpoint (that is *GKE Control Plane Exposure*).
* **Load Balancer Edge** *(v18.3, Investigation Recommended)*: The external load balancers' edge, from the inventory — an **HTTP-only** load balancer (a forwarding rule to a target HTTP proxy whose URL map has no HTTPS rule: cleartext at the edge); **weak TLS** (a target HTTPS or SSL proxy without an SSL policy — the default allows TLS 1.0 — or one below TLS 1.2 or on the `COMPATIBLE` profile; CIS 3.9); an external backend service, global or regional, **without Cloud Armor** (no WAF rules, rate limiting or adaptive protection) or **without logging**; since v18.6, **IAP over HTTP** — a backend service with Identity-Aware Proxy on behind an HTTP-only load balancer (its session cookie and identity headers cross the internet in clear). Each row carries the `gcloud` line; internal load balancers are not judged.
* **DNS Posture** *(v18.3)*: A public zone with **DNSSEC off** (CIS 3.3, *Investigation*), a zone signing with **RSASHA1** (CIS 3.4/3.5, **Action Required**), and a VPC network **without a Cloud DNS logging policy** (CIS 2.12, *Investigation*: no record of what resolved what).
* **BigQuery Governance** *(v18.4)*: A dataset whose ACL admits `allUsers` or `allAuthenticatedUsers`, and a dataset or **table** whose IAM policy does (one IAM-policy search under the scope; the dataset's own ACL is not repeated) — **Action Required** (CIS 7.1: anyone on the internet, or any Google account, reads it); a dataset whose **time-travel window** is below the seven-day default — a dropped table or a bad `DELETE` is recoverable for that long only — graded since v18.6 by the storage billing model: *Investigation* under logical billing (time-travel bytes are not billed there, so the shorter window saves nothing), *Informational* under physical billing (a deliberate trade-off, the Detail says so). Each row carries the `bq` line.
* **Cloud SQL Flags** *(v18.4)*: The CIS §6 flag pack of each engine, an unset flag read as its **engine default** — MySQL `local_infile` (**Action Required**: a client can read the server's files) and `skip_show_database`; PostgreSQL `log_connections`, `log_disconnections`, `log_error_verbosity`, `log_min_messages`, `log_min_error_statement`, `log_min_duration_statement`, `log_statement` and `cloudsql.enable_pgaudit` (the level flags judged on their ordered scales); SQL Server `external scripts enabled`, `cross db ownership chaining`, `remote access` and `contained database authentication` (**Action Required**), `user connections`, `user options` and trace flag `3625` — one row per failing flag with its CIS item, the fix a `gcloud sql instances patch --database-flags=` line that **keeps the flags already set** (patch replaces the whole list). Read replicas inherit their primary's flags and are not repeated. Since v18.6 a `Note` column says where Google's Workload Manager best-practice rule points the other way (`log_min_duration_statement`, trace flag `3625`, `user connections`) — the rows follow CIS. *(v19.3)* notes `cloudsql.iam_authentication` off as Informational — Google's recommendation (short-lived tokens, no database passwords), not CIS's requirement.
* **KMS Keys** *(v18.4)*: A **symmetric** key with no rotation period, with one above 90 days, or whose next rotation is overdue (CIS 1.10, *Investigation*; asymmetric, MAC, disabled and destroyed keys are not judged); a key ring or key whose IAM policy admits the public (**Action Required**); a principal holding `roles/cloudkms.admin` **and** an encrypter or decrypter role on the same resource (CIS 1.11, separation of duties, *Investigation*) — from one IAM-policy search on the KMS roles under the scope.
* **API Keys** *(v18.4, Investigation Recommended)*: A key **without an application restriction** (any website, server or app that obtains it can use it; CIS 1.13), **without an API restriction** (it reaches every API the project has enabled; CIS 1.14), or **older than 90 days** (CIS 1.15), with the `gcloud services api-keys update` line. That a project has API keys at all is not a row (the inventory names keys by project number; the rows name the project by ID).
* **VM Service Accounts** *(v18.5)*: A VM that runs as the Compute Engine or App Engine **default service account** — **Action Required** when the account holds a privileged role (owner, editor, the IAM and service-account admin roles, container and compute admin, storage and Secret Manager admin; read with the IAM search GKE Credential Exposure runs) or the VM has the `cloud-platform` scope (CIS 4.2), *Investigation* otherwise (CIS 4.1). The row names the role and what the scopes let a stolen token call; stopped instances are judged and say so; a dedicated account is never a row; GKE, Dataproc, Dataflow and Workbench fleets are judged by their own checks, not here. The instances are read from the Compute API per project with VMs (the inventory says which projects those are, and stands in when the API is refused). The fix is `set-service-account` on the stopped instance, or the instance template for an instance a managed instance group created.
* **VM Hardening** *(v18.5, Investigation Recommended)*: Per **project**, one row each (the common instance metadata read from the Compute API — the inventory lags it and omits `ssh-keys`): OS Login off (CIS 4.4, with how many instances rely on metadata keys), project-wide SSH keys in use while OS Login is off (CIS 4.3, with how many instances they reach), the serial console enabled project-wide (CIS 4.5). Per **instance**: an OS Login opt-out, the serial console, IP forwarding (CIS 4.6 — legitimate for a router or NAT appliance, the row says so), Shielded VM off (CIS 4.8: vTPM or integrity monitoring, or an image that is not Shielded-capable), Secure Boot off (some images lack signed bootloaders — then a documented exception). Each row carries the `gcloud` line.
* **Service Account Privileges** *(v18.5)*: A service account holding a predefined **administrative role** (`roles/*.admin`, `roles/*Admin`) at project, folder or organization level — beyond what Primitive Roles and Critical Org-Level Roles report — *Investigation*; **Action Required** when the role grants the power to change who may do what (`iam.securityAdmin`, `resourcemanager.projectIamAdmin`, the service-account admin roles, `orgpolicy.policyAdmin`, `iam.denyAdmin`, `iam.organizationRoleAdmin`, folder and organization admin, `billing.admin`) or the holder is a **default service account** (CIS 1.5); one principal holding `iam.serviceAccountAdmin` **and** `iam.serviceAccountUser` or Token Creator on one resource (CIS 1.8, separation of duties). Custom roles are not judged by name; Google-managed service agents are never rows. From one listing of the IAM policies under the scope; projects named by ID.
* **External Principals** *(v18.5)*: Users and groups outside the organization's primary domain and `TRUSTED_DOMAINS` (*Investigation*: an acquired company's domain as often as a stranger), consumer accounts and external `domain:` grants (**Action Required**; CIS 1.1), deleted principals still bound, a folder open to the public (**Action Required**; projects are Primitive Roles' subject, the organization Public Org-Level Access'), a custom image open to the public (**Action Required**). One row per (resource, principal) with the roles joined and the removal lines.
* **Unused Service Accounts** *(v18.5, Investigation Recommended)*: The IAM recommender's service-account insights — accounts without an authentication in Google's 90-day window — one row each with the last authentication date (or *never*), default accounts included (disable, never delete), `gcloud iam service-accounts disable` as the fix.
* **Serverless Exposure** *(v18.6)*: The first look at Cloud Run and Cloud Functions — a service or function **behind an external load balancer** (a serverless NEG in an external backend service) whose ingress is still `all`: callers reach the `run.app` URL and bypass the load balancer and whatever Cloud Armor policy it carries (**Action Required**; *Investigation* when IAP on the service still authenticates them); a **public** one — `allUsers` or `allAuthenticatedUsers` on the invoker role **or the invoker IAM check disabled** (the newer setting, which no IAM search sees) — with ingress `all` and no IAP (*Investigation*: legitimate for a public site, the row says what makes it public and names IAP or an authenticated caller as the alternatives). IAP-fronted and internal services are never rows; second-generation functions are judged through their Cloud Run service. The services, jobs and their invoker policies are read from the Cloud Run v2 API per project that has any (the inventory says which; it stands in when the API is refused), functions from the Cloud Functions v2 API, and the backend services in front of them from the Compute API. Rows `Project, Workload, Location, Kind, Ingress, Invoker, Issue, Detail, Fix`.
* **Serverless Service Accounts** *(v18.6)*: A Cloud Run service or job, or a function, that runs as the Compute Engine or App Engine **default service account** (or none, which is the Compute default) — **Action Required** when the account holds a privileged role (the v17.1 list, read with the IAM search VM Service Accounts runs), *Investigation* otherwise: a Cloud Run token has no scope limit, every role of the account is reachable from the container. The fix creates a dedicated account and points the workload at it; a dedicated account is never a row.
* **Cloud Armor Policy Content** *(v18.6)*: Inside the **attached L7 policies** (`type` `CLOUD_ARMOR`; network and edge policies carry no WAF rules by design): a rule on an **older ruleset generation** (`sqli-stable`, `xss-v33-stable`, …) or on the legacy `evaluatePreconfiguredExpr` syntax — *Investigation*, the Detail naming the current ruleset, the signature gap (RCE 15 → 44) and the retired signature IDs to drop from the opt-out list, the Fix the current rule in preview; a policy that **protects nothing** (only the default rule, or allow rules over a default allow, no WAF rule, no deny or throttle, Layer-7 DDoS defense off); a policy whose deny rules are **all in preview**; and the housekeeping rows — preview rules left behind, 180 of the 200-rule quota (*Informational*). The ruleset generations ship in `assets/cloud_armor_rulesets.json`; the policies are re-read from the Compute API per project. Unattached policies get no row.
* **Container Scanning Enabled** *(v18.6, Investigation Recommended)*: A project with standard **Docker repositories** in Artifact Registry (gcr.io redirect repositories included) and Artifact Analysis (`containerscanning.googleapis.com`) **not enabled** — no image pushed to it has ever been scanned for known CVEs; one row per project, the Fix the one `gcloud` line that turns the API on (billed per image scanned); the service's state is re-read from the Service Usage API per project with such repositories, so the fix shows on the next scan. Remote and virtual repositories are not counted.
* **Folder Primitive Roles** *(v18.7)*: Owner or Editor on a **folder** — nothing read folder-level IAM before — by kind of holder, the same table as Primitive Roles (a service account, a consumer account or a whole domain **Action Required**; a person, a group or a default service account *Investigation*), plus **Project Creator on a folder** (a whole domain **Action Required**, a person *Investigation*, a group or a service account the project-factory practice, listed). Every project below the folder inherits the grant; the row counts them. Fresh `folders.getIamPolicy` per folder under the scope, the IAM-policy search's copy when a read is refused (said under *Projects not checked*). Google-managed agents are never rows; a public principal on a folder stays External Principals' row.
* **Privileged Grants** *(v18.7)*: At the organization *(organization scans)*: **Project Creator** held by a whole domain or the public (**Action Required** — every account can create projects), by a person (*Investigation*), by a group or an automation account (listed); the **billing roles** `billing.creator`, `billing.user`, `billing.viewer`, `billing.costsManager` granted at the organization (they belong on the billing account — *Investigation*; a domain or the public **Action Required**; `billing.admin` stays Critical Org-Level Roles' row); **Organization Administrator redundancy** — fewer than two principals holding the role without a condition (**Action Required**, Informational when the one is a group); one Informational row when **no IAM deny policy** is attached to the organization. Under every scope: **Privileged Access Manager entitlements** that hand out an administrative role with no approval workflow (*Investigation*), that last over 24 hours or need no justification (Informational), and a **standing grant that duplicates an entitlement** — the same principal and role, unconditionally, where PAM would grant them on request (**Action Required**). A split check: the organization, its folders and their entitlements in the scope shard, the projects' entitlements per shard (a project without the PAM API is not a row).
* **Secret Access Scope** *(v18.7)*: `secretmanager.admin`, `secretmanager.secretAccessor` or `secretmanager.secretVersionManager` granted **resource-wide** — on a project, a folder or the organization — rather than on a secret: to the public or a whole domain **Action Required**; to a service account *Investigation* (every workload and key of the account can read every secret under the resource); to a person or a group *Investigation* with at least one secret in reach, Informational with none. One IAM-policy search for the three roles; the secrets in reach counted from the inventory. The fix removes the grant and names the per-secret binding.
* **Secret Manager Posture** *(v18.7)*: From the inventory's copy of the secrets and their versions (the Secret Manager API would need `roles/secretmanager.viewer`, which the account does not hold; the inventory never carries payloads): a secret whose **newest enabled version is older than 90 days with no rotation schedule** (*Investigation* — a static credential), **user-managed replication in one location** and a secret with **no enabled version** (Informational).
* **Custom Roles With IAM Powers** *(v18.7)*: A custom role — the organization's *(organization scans)* or a project's — carrying a permission that changes who may do what: any `*.setIamPolicy`, `iam.serviceAccountKeys.create`, `iam.serviceAccounts.actAs` / `getAccessToken` / `signBlob` / `signJwt` / `implicitDelegation`, `iam.roles.create` / `update`, `orgpolicy.policy.set` — *Investigation* when a principal that is not a Google-managed agent holds it (the row names the holders from the IAM-policy search), Informational when dormant; a **retired** role (disabled, deprecated or deleted) still bound, Informational. Fresh `roles.list` with `view=FULL`; predefined roles are Service Account Privileges' and Critical Org-Level Roles' ground.
* **User-Managed Keys** *(v18.7)*: One row per service account with **any user-managed key that can still authenticate** (not disabled, not expired, the account enabled) — the count, the oldest key's age, the expiry (`never` ×N, the earliest dated one) and the origin (created in Google Cloud or uploaded) — *Investigation* (CIS 1.4): a long-lived credential that works from anywhere for whoever holds the file; the fix disables the oldest key once the caller uses an attached service account, impersonation or Workload Identity Federation, and names the two organization policies that stop new keys. The second record of the key listing SA Key Rotation already makes; the rotation rows (keys older than 90 days, **Action Required**) are unchanged.
* **SCC Active Findings** *(v19)*: What **Security Command Center** currently says about the scope — the active, unmuted findings (SCC v2, under the roles the scanner already holds; a folder scan reads the organization's and keeps the folder's projects), one row per class × category × severity with the count, the first resources, the newest event time, SHA's own recommendation, and a **CloudGauge check** column naming the record in this report that judges the same fact ("—" marks a fact this report has no check for — CloudGauge's own gap list). SCC's severity is the verdict: CRITICAL **Action Required**, HIGH and MEDIUM *Investigation*, LOW and observations Informational, an `SCC_ERROR` finding (SCC itself misconfigured) *Investigation*. An organization scan adds a row when findings are **exported nowhere** (no notification config, no BigQuery export): Informational at the Standard tier, *Investigation* at Premium or Enterprise. Whatever it lists, the record is **one check** in the score — a fact that also fails its CloudGauge record costs the category two checks, never two plus the rows.
* **SCC Detector Coverage** *(v19)*: Per project, the *effective* state of the detector services (`securityCenterServices.list` — the organization's own list says *inherited → disabled* while a project may run five services): **Security Health Analytics off** is **Action Required** — the project is never scanned, no misconfiguration finding will ever appear for it; Event, Container, VM and Cloud Run Threat Detection and Web Security Scanner off are *Investigation* where the project runs another threat detector (its Premium-tier services are on, this one was left off), Informational where it runs none (the detector needs a higher tier) — judged per project, so a sharded scan reads as a single one. Module states are counted, not judged. *Security Command Center Status* (the organization's tier) is unchanged beside it.
* **OS Vulnerabilities** *(v19)*: Per zone with running VMs outside the managed fleets, **VM Manager's vulnerability reports**: an instance with **critical CVEs that have a fix available** is **Action Required**, with **high** ones *Investigation* (the three worst CVEs named with their CVSS; the fix is an OS Config patch job on the instance); the rest are counted. A project where the API answers *vulnerability reports are disabled* gets one Informational row — full VM Manager is not enabled, the CVEs on its VMs are unknown to Google Cloud and to this report.
* **Exposed Privileged VMs** *(v19)*: CloudGauge's own toxic combination, joined from one listing of the scope's instances, VPC firewall rules and firewall policies and the project IAM policies: a running VM with an **external address**, a **privileged identity** (the default compute account with the `cloud-platform` scope, or a service account holding Owner, Editor, an `*.admin` or an `iam.*` role on the project) **and** an enabled ingress allow rule from `0.0.0.0/0` or `::/0` that reaches it (its network; no targets, or a matching tag or service account) — **Action Required**, the row naming all three, the fix removing the address. Two legs are not a row: each has its own record.
* **Organization Policy Exceptions** *(v19.3)*: The guardrails the scanned resource **holds** that a folder or project **below** it weakens. *Organization Policies* judges the policies as *effective at the scanned resource* — true, and blind to everything under it: a folder or project can set `enforce: false`, `reset`, `allowAll`, add allowed values or cut inheritance, and an organization scan still reads Compliant. This record reads **one Asset Inventory listing** of every organization policy set at every level under the scope (`orgpolicy.googleapis.com/Policy`, with each policy's ancestors) and the folders and projects under it, computes the **effective policy of every container in memory** with Resource Manager's own rules (boolean nearest-wins and `reset`; list `inheritFromParent` merge against replace, `allowAll`/`denyAll`; tag-conditional rules for tagged resources only), and writes one row per policy set below that weakens a best-practice constraint the scanned resource holds: `Constraint, Set on, Above, Below, Reaches` (the projects it affects), the restore line (`gcloud org-policies delete … --folder|--project` — back to inheritance; a deliberate exception belongs in a tag-conditioned rule, where it is scoped and visible). Unconditional → **Action Required**; tag-conditional → *Investigation Recommended*; policies set below that tighten, restate, name constraints outside the table or address a gap the scanned resource has itself → one Informational count line (the all-clear is evidence). A project scan has nothing below it and says so. No per-project call, no new role or API; scales to thousands of projects. The *Organization Policies* table gains a **Below** column ("*2 exceptions (folders/…, projects/…)*") when the scan found any, and the Scorecard's sentence says how many guardrails have exceptions below — the table's verdict stays what it truthfully is at the scanned resource; the exception is **one check** in the score whatever it lists.
* **GKE Control Plane Activity** *(v19.1)*: The detective half of the SSRF chain — what was **done** to the clusters in the last **7 days**, from each project's Admin Activity audit log (one `entries.list` per project — the `k8s_cluster` log is a project's, and a read of the organization returns only the organization's own entries — newest first, 2,000 entries per project at most; a capped read says so): `exec`, `attach` and `port-forward` into pods, DaemonSets and CronJobs created in `kube-system`, bindings to `cluster-admin` created or changed, admission webhooks created or changed — grouped by cluster, action, principal and where the call came from (an **internal** address — `private`, RFC 1918, loopback, link-local — or an **external** one). Google's own principals are left out (`system:*` except workload service accounts outside the GKE-managed namespaces, the `gcp-sa-*` agents, `@system.gserviceaccount.com`, the GKE robot): on the reference organization every control-plane write of a month was theirs. A user's exec is *Informational* (operations, named); a service account's is *Investigation Recommended*, **Action Required** from outside; `cluster-admin` granted is *Investigation Recommended* by a user, **Action Required** by a service account; `kube-system` workloads and webhook changes *Investigation Recommended*, **Action Required** by a service account from outside (an external address escalates service accounts only — people work from laptops, which are outside by nature). A refused call (RBAC, IAM, an organization policy) counts and is said — an attempt is a signal. Secrets reads are Data Access logs — not recorded on most organizations and not readable by `roles/logging.viewer` — and are not judged; the all-clear says so. Every row's fix is the `gcloud logging read` that shows the events, then the RBAC or the access to remove.
* **Service Account Activity Signals** *(v19.1)*: Over the same 7 days of Admin Activity logs — the organization's or folder's own entries (an IAM change on the organization is written there) and every project's — what **service accounts** (not people, not Google's own) did with identity: created a **key**, changed an **IAM policy** (project, folder, organization or service account), wrote **instance or project metadata** — *Investigation Recommended*, **Action Required** from an external address; created a service account — *Informational* (a project factory does). Grouped by project, principal, action and address class with the targets and the latest time; refused calls counted and said. Token minting (`GenerateAccessToken` and friends) is a Data Access log and is not read; the all-clear says so. The fix line reads the principal's week, then names the role to remove.

> **The SSRF chain** *(v17.1)*. The six checks above follow one intrusion pattern, each breaking a link: a server-side request forgery in an internet-facing pod reaches the node's metadata server → the token of a default service account holding Editor is stolen → replayed from outside Google Cloud → chained through broad Token Creator grants into most of the project's service accounts and neighbouring projects → used against a publicly reachable control plane — with no perimeter to stop the replay and no runtime detection to raise an alarm. CloudGauge gives the posture facts, the fix lines and the *one SSRF from Editor* verdict; Security Command Center Premium or Enterprise remains the answer for runtime detection (Container and Event Threat Detection) and workload CVEs, and *GKE Threat Detection* tells you which clusters it actually covers. The Organization Policies check evaluates the matching guardrails (`container.managed.enableWorkloadIdentityFederation`, `disallowDefaultComputeServiceAccount`, `enablePrivateNodes`, `enableNetworkPolicy`, `disableRBACSystemBindings`, `enableSecurityBulletinNotifications`, `enableBinaryAuthorization`, `enableControlPlaneDNSOnlyAccess`, `enableSecretsEncryption`, `enableGoogleGroupsRBAC`) so that new clusters cannot reopen the chain. Nothing here needs a new role; the perimeter check needs the Access Context Manager API enabled in the project CloudGauge runs in (`tools/deploy.sh` does it).

## Cost Optimization

* **Idle Resources**: Finds idle Cloud SQL instances, VMs, persistent disks, unassociated IP addresses and, since v17, idle custom images. Every recommender listing asks for the recommendations still **active** *(v18)*: one that was applied or dismissed is not a finding, and a recommendation that would cost more (an upsize for performance) is not counted as a saving. *Idle Load Balancers* was retired in v18 — the recommender it named does not exist, so it had never reached a verdict. Since v18.1 every recommendation row carries its **Priority** (`P1` … `P4`) and a **Fix** — the `gcloud` line that applies it, or the console path where the action is a purchase — and the verdict follows the priority: `P1`/`P2` **Action Required**, `P3`/`P4` *Investigation Recommended*.
* **Rightsizing**: Identifies overprovisioned VMs and underutilized reservations and, since v17, overprovisioned Cloud SQL instances and Cloud Run services whose CPU allocation could change; since v18.1, **MIG Rightsizing** — managed instance groups whose machine type the recommender would change.
* **Commitments** *(v17)*: **Resource-Based Commitment Recommendations** (Compute Engine committed use discounts, per project and region); **BigQuery Slot Commitments**; **Commitments Expiring** — active commitments that end within 90 days without renewing, with the `--auto-renew` line. Spend-based commitments live on billing accounts, whose access is centralised in most organizations: CloudGauge never asks for a billing-account role — the *Forecasts, budgets and spend* release (v18.8 on the roadmap) reads them from the organization's Recommender export to BigQuery instead.
* **Cost Allocation Labels** *(v17)*: The projects missing one of the label keys named in `COST_ALLOCATION_LABELS` (`cost-center,environment,owner`, say), with the `gcloud projects update --update-labels` line. Unset, the check is *Informational* and says how to configure it — it never moves the Efficiency score until it is.
* **Cloud Storage Lifecycle** *(v17)*: Buckets with neither lifecycle rules nor Autoclass, whose objects never move to a colder class or expire (*Investigation Recommended*), plus the **Cloud Storage Soft Delete** recommender. Since v18.8 also a **versioned bucket with no lifecycle rule that deletes noncurrent versions** — every overwritten or deleted object keeps a billed copy for ever; the fix writes the bucket's rules plus one that keeps the three newest noncurrent versions (one line: the merged lifecycle to a file, then `--lifecycle-file`).
* **Snapshot Sprawl** *(v17)*: Disk snapshots older than `SNAPSHOT_MAX_AGE_DAYS` (90) or whose source disk no longer exists, under the scanned scope, with their age and size.
* **Spend Briefing** *(v18.8, briefing)*: What the scanned scope pays, read from the organization's **billing export in BigQuery** (`BILLING_EXPORT=<project>.<dataset>`, the standard usage cost tables `gcp_billing_export_v1_*`; `roles/bigquery.dataViewer` on that dataset alone — CloudGauge holds nothing on any billing account): **month to date** against the same days last month, a **forecast** (month to date plus the mean of the last seven complete days over the days remaining), **last month** and the month before, the top projects and services of the last 30 days with their share and change, the credits by type with the **committed-use coverage** of the commitment-eligible services (0 % = nothing committed), and the export's freshness. Every line carries the `bq query` that reproduces it. The scope is the scan's: an organization's or a folder's rows by the project's ancestry, a project's by its ID. *Informational*, outside the score; unset, both spend records say how to configure it. The Scorecard's **Efficiency** line starts with the three headline numbers.
* **Spend Anomalies** *(v18.8)*: A project's spend on a service over the last seven complete days at least **1.5 ×** the weekly mean of the three weeks before and at least the floor (`SPEND_ANOMALY_FLOOR`, 50 in the export's currency, or 2 % of last month's net when that is higher), or **new spend** of at least the floor — *Investigation Recommended*, with the SKU-breakdown query as the fix. Drops are not rows (a stopped workload is the usual cause; the briefing's deltas show them). The rule runs in SQL: only the flagged pairs come back.
* **Log Cost Levers** *(v18.8)*: Per project, the three settings that decide most of a Cloud Logging bill: a log bucket other than `_Required` **kept beyond the 30 days** included with ingestion (Informational — compliance may want it; the row says the paid days, and that a locked bucket cannot be shortened), a subnet with VPC flow logs **sampled above 0.5** (*Investigation*; all metadata and the 5-second interval go into the fix when set), and **DEBUG entries at 10 % or more** of a project's 30-day log volume above the 50 GiB free tier with no exclusion on the `_Default` sink that drops them (*Investigation*). Buckets and sinks from the Logging API, subnets from the Compute API, the volume by severity from Cloud Monitoring (`logging.googleapis.com/byte_count`). `_Required` streams, Data Access logs and the severities above DEBUG are never proposed for exclusion.
* **Serverless Cost Hygiene** *(v18.8)*: A Cloud Run service, job or gen-2 function whose egress goes through a **Serverless VPC Access connector** (its instances bill around the clock; Direct VPC egress scales to zero — the fix moves it, naming the connector's network and subnet), a connector **no workload uses**, and a workload whose **Cloud SQL instance is in another region** (cross-region egress and latency on every query) — all *Investigation*. One listing of the scope's workloads and connectors, then the Cloud Run v2 and VPC Access APIs per project that has any, so a deleted connector or a moved service clears on the next scan.
* **Duplicate Log Routing** *(v18.9)*: An **aggregated sink** at the organization or a folder in scope that stores logs in a **log bucket** (its filter admitting what `_Default` keeps) while the projects below keep their `_Default` sinks enabled — every entry stored twice and ingestion billed twice (*Investigation*, one row per aggregated sink counting the projects and naming the first five; the fix disables or narrows); a sink into a user bucket whose filter admits the **`_Required` streams** (Admin Activity, System Event, Access Transparency), which `_Required` already keeps 400 days free (Informational — a longer or locked archive does it on purpose). Sinks into BigQuery, Cloud Storage or Pub/Sub carry no Logging ingestion charge and are not rows.
* **Detailed insights** *(on demand)*: The Cost Optimization page's **Get detailed insights** button asks the Recommender's insight types for every project in scope — CPU and memory usage, idle images, and more — and renders them in the page without re-running the scan.
* The Scorecard's **Efficiency** line sums the estimated monthly savings of every failing cost check, per currency ("1,234.56 USD/month in identified savings") and, with `BILLING_EXPORT` set, opens with the spend ("month to date 975.81 USD, forecast ≈ 1,938.43 USD, last month 1,927.37 USD"; v18.8). The score itself never counts the briefing.

## Reliability & Resilience

* **Essential Contacts**: Ensures a contact is subscribed to the `SECURITY`, `TECHNICAL`, `LEGAL` and `SUSPENSION` categories (a contact subscribed to `ALL` covers them all) — the organization's own contacts in an organization scan, the *effective* contacts (inherited ones included) of a folder or project otherwise *(v18.1; organization scans only before)*. A contact whose address bounced does not count; the Compliant row names who receives each category.
* **Service Health Incidents** *(briefing)*: What Personalized Service Health has told the scanned projects in the last 90 days, organization-wide: the incidents it classed *Impacted*, plus the *Related* ones confined to specific locations (the evidence **Incident Exposure** reads), one row per incident naming every project it touched, active incidents first. Global *Related* incidents — a product-wide event lists every region — are counted in a note under the table, not listed; `SERVICE_HEALTH_RELEVANCE=IMPACTED,RELATED` lists them all. Always *Informational* and never on the Scorecard: a Google-side incident is not the customer's posture *(v17.3)*. `SERVICE_HEALTH_INCIDENTS=off` removes the briefing (and Incident Exposure) from a deployment. The window is `SERVICE_HEALTH_WINDOW_DAYS`.
* **Personalized Service Health API Coverage**: Flags every project in which the Service Health API is not enabled (*Action Required*): such a project has no personalized incident view, alerts or relevance.
* **Cloud SQL Resilience**: Checks every Cloud SQL instance under the scanned organization, folder or project (Cloud Asset Inventory) for High Availability (HA) configuration, automated backups, backup retention (at least 30) and Point-in-Time Recovery (PITR). Each of the four checks reaches a verdict: *Action Required* with the instances, or *Compliant* with an all-clear row.
* **GCS Versioning**: Versioning where the practice asks for it *(v18.1)*: a bucket a log sink writes to without object versioning is **Action Required** (CIS 2.3); any other bucket is a row only when nothing protects its objects at all — versioning off, soft delete off, no lifecycle rule, no retention policy (*Investigation Recommended*). A bucket with the default seven days of soft delete passes; a bucket under a retention policy is protected by it (and cannot have versioning besides). Before v18.1 every bucket without versioning was flagged. Zonal (Rapid Storage) buckets support none of the four protections and are not judged *(v18.6)*.
* **GKE Hygiene**: Clusters not on a release channel and node pools with auto-upgrade or, since v18.1, auto-repair disabled (**Action Required**, with the `gcloud container … update` line), and Active Assist's GKE diagnosis recommendations, each attributed to the cluster it names *(v18; Investigation Recommended)*.
* **GKE Cluster Resilience** *(v17.3)*: Zonal control planes and single-zone node pools — the two shapes one zone's incident takes down — from the same cluster listing as the security checks, with the `--node-locations` line for a pool (a zonal control plane cannot be made regional in place; the fix says so). Autopilot clusters are regional and have none.
* **SSL Certificate Health** *(v18.6)*: The certificates the target HTTPS and SSL proxies serve — a **self-managed** certificate expiring within 30 days (*Investigation*; **Action Required** within 7 days or expired, the Fix a replacement certificate on the proxy — a Google-managed one renews itself), a **Google-managed** certificate that failed to provision or renew, or any of its domains (**Action Required**: it will not issue until the domain's records point at the load balancer; the old certificate serves until it expires, then nothing) or stuck provisioning for more than a day, and an unattached expired certificate (*Informational*, housekeeping). Re-read from the Compute API per project; Certificate Manager certificates are a different asset and not read.
* **Synthetic and SLO Coverage** *(v18.9)*: Whether anything watches the edge from outside and whether anybody agreed on a target: an **external load balancer** (external forwarding rules, regional and global, from one listing under the scope) with **no uptime check** targeting its address — or any hostname, which the scanner does not resolve — in its project (*Investigation*, with the `gcloud monitoring uptime create` line); an **uptime check with no enabled alert policy** on it (`check_passed` for its check ID, or for every check); an **SLO without a burn-rate alert** (no enabled policy selecting `select_slo_*` on it) — *Investigation*; a project running external load balancers, Cloud Run services or GKE clusters with **no SLO at all** (Informational). Uptime checks, services, SLOs and policies come from the Monitoring API of each project that runs one of those; ones kept in a metrics scoping project are not seen.
* **GKE Upgrade Readiness** *(v18.2)*: What stands between a cluster and a clean upgrade, from the cluster listing (re-read from the GKE API per project, because the inventory's copy can lag a maintenance-policy change by hours) and one listing of its PodDisruptionBudgets in Cloud Asset Inventory — no cluster credentials. **No maintenance window** (GKE chooses the time: upgrades can land in business hours) and **upgrade notifications off** or filtered without security bulletins (*Investigation Recommended*, with the `clusters update` lines); an **active maintenance exclusion** as a calendar row (*Informational*: scope and the date upgrades resume); a Standard node pool whose surge settings **lose capacity** during an upgrade (`maxUnavailable` ≥ 1) or that sits **two minors behind** its control plane (*Investigation* when auto-upgrade is off — the control plane cannot move until the pool does; *Informational* when GKE will move it); and the **PodDisruptionBudgets** of the workloads: a budget that can never be satisfied (`maxUnavailable: 0`, `minAvailable: 100%`, or an absolute minimum not below the pods it expects) is **Action Required** — no node running that workload can ever be drained, so upgrades stall (GKE waits an hour per node, then proceeds) and scale-down never happens; a budget allowing no disruption *right now* (`disruptionsAllowed: 0`) is *Investigation* (a snapshot: the inventory lags the cluster by minutes). Budgets in the system namespaces (`kube-*`, `gke-*`, `gmp-*`, Config Management) are Google's and are not judged; Autopilot clusters get the cluster-level rows only.
* **Hybrid Connectivity** *(v18.3)*: What keeps a site connected — a VPN tunnel that is **not established** (**Action Required**, with the API's detailed status; the state is re-read from the Compute API, not the inventory's copy); an HA VPN gateway whose tunnels all sit on **one interface**, or that has none (**Action Required**: no redundancy, no SLA); a **Classic VPN** gateway (*Investigation*: deprecated); Dedicated/Partner **Interconnect** with fewer than two attachments per Cloud Router or all in one edge availability domain, or an attachment that is not active (**Action Required** — Google's 99.9 % topology needs two in different domains); a Cloud Router with **one BGP peer for two links** (*Investigation*). Each row carries the `gcloud` line that adds the missing half.
* **VPC Peering & Cloud NAT** *(v18.3, Investigation Recommended)*: A peering that is **not active** (the other network has not peered back: no traffic flows); peered networks with **different MTUs** (packets above the smaller MTU are dropped or fragmented — resets, timeouts, container DNS failures; reported once per pair, Google-managed peers not judged); a Cloud NAT **without logging** (port exhaustion is invisible); a Cloud NAT on **static port allocation at the default 64 ports per VM** (connection-heavy VMs run out of ports). Secure Web Proxy's auto-generated NATs are not judged.
* **AlloyDB Posture** *(v18.4)*: A cluster without **automated backups** (**Action Required**: a bad migration or a deleted cluster is unrecoverable) or without **continuous backup** (*Investigation*: no point-in-time recovery); a **zonal primary** (one zone's incident takes the database down); an instance with a **public IP**; an instance whose `sslMode` is not `ENCRYPTED_ONLY`; the PostgreSQL log flags (`log_connections`, `log_disconnections`, `log_error_verbosity`, `log_min_messages`, `log_min_error_statement`) — *Investigation Recommended*, each with its `gcloud alloydb … update` line. *(v19.3)*: a public instance whose **authorized external networks** include `0.0.0.0/0` or `::/0` is **Action Required** (the public IP alone stays *Investigation*).
* **Incident Exposure** *(v17.3)*: What you ran, without failover, in a location where the product you ran had an incident. Derived from the scan itself — no API call: for each location-specific incident of the briefing, the zonal Cloud SQL instances, zonal MIGs, single-region snapshots, zonal control planes and single-zone node pools of the projects it touched, in the locations it named, in the product it concerned (a Compute Engine incident meets MIGs and snapshots, not Cloud SQL instances; a zone counts for its region). One row per asset with the incidents as evidence and the fix; *Compliant* when incidents met footprints that all had failover; *Informational* when no location-specific incident in Compute Engine, Persistent Disk, GKE or Cloud SQL touched the scanned projects (nothing to assess — the Resilience checks keep flagging the assets). Incidents in products the tool has no footprint for are counted in a note. Its row count is the Scorecard's Stability sentence: *3 assets without failover in locations that had incidents*.
* **GKE Supported Versions**: Finds control planes and node pools on a GKE minor that is no longer offered (*Action Required*) or on the oldest minor still offered — the next to leave support (*Investigation Recommended*). The reference is GKE's own `getServerConfig` for the cluster's location: a cluster on a release channel is judged against its channel's versions, one without against the static lists. Every row carries the `gcloud container clusters upgrade` command to the right target (a node pool never beyond its control plane).
* **Resilience Assets**: Identifies zonal MIGs (recommends regional) and disk snapshots stored in a single region (a snapshot kept in a multi-region — `asia`, `eu` or `us` — passes), named one by one with their location, under the scanned scope; an all-clear row when there are none. *(v19.3)* adds **Cloud SQL Deletion Protection** — instances without deletion protection (*Investigation Recommended*: one `delete` or a Terraform destroy removes the instance and its backups) and without a maintenance window (Informational) — from the same listing.
* **Cloud SQL Extended Support** *(v17)*: Instances on a database version in extended support (*Action Required*: MySQL and PostgreSQL pay the fee, SQL Server follows Microsoft's lifecycle) or within 180 days of entering it (*Investigation Recommended*), from a static table of the published dates, with the in-place `gcloud sql instances patch --database-version` upgrade line.
* **Capacity Commitments** *(v17, briefing)*: Every reservation, future reservation and committed use discount of the scanned projects — what, where, how much, in use, status, when it ends. Always *Informational*.
* **Reservation Coverage** *(v17)*: A project running `RESERVATION_COVERAGE_MIN_VCPUS` (32) or more vCPUs in one zone with fewer reserved there — steady compute a zonal stockout or a maintenance event has nowhere to put — with the `gcloud compute reservations create` line for the zone's most common machine type.
* **Capacity Signals** *(v17)*: The Compute Engine operations of the last 30 days that failed for want of capacity (`ZONE_RESOURCE_POOL_EXHAUSTED`) or of quota (`QUOTA_EXCEEDED`), from Cloud Logging, grouped by project, zone, machine type or accelerator and kind; *Action Required* when a signal is younger than 7 days.

## Operational Excellence & Observability

* **Organization Log Sink** *(organization scans)*: Whether an organization-level sink exports the audit logs of the whole organization *(v18.1)*: the built-in `_Required` and `_Default` sinks do not count; a customer sink qualifies when it is enabled, includes children and its filter admits the audit logs. One row per customer sink with its destination, filter, state and assessment — a qualifying one is Compliant, sinks that all fall short *Investigation Recommended*, none **Action Required** with the `gcloud logging sinks create … --include-children` line. (Before v18.1 the built-in sinks counted, so the check could not fail.)
* **Data Access Audit Logs** *(v18.1)*: Whether the three Data Access log types — `ADMIN_READ`, `DATA_READ`, `DATA_WRITE` — are on for every service, with nobody exempted, in the IAM policy of the scanned resource: the organization's in an organization scan; the folder's or project's and its ancestors' otherwise (their union is what applies). Nothing configured anywhere is **Action Required** — reads and writes of data leave no audit trail (CIS 2.1); a partial configuration or an exemption *Investigation Recommended*. One row naming what is on, what is missing, who is exempted, where it is configured and the services configured individually, with the `set-iam-policy` recipe and the cost caveat on `DATA_READ`.
* **OS Config Agent Coverage**: Running VMs without an OS inventory, one row per VM with its zone and the `enable-osconfig` metadata line *(v18)*. One inventory listing per zone (what `roles/iam.securityReviewer` grants); a project with OS inventory management or the OS Config API off is one *Action Required* row with the project-wide fix, and a project the scanner could not read is under *Projects not checked* — before v18 both listed every VM as not reporting. GKE and Autopilot nodes, Dataproc, Dataflow and Batch workers are excluded.
* **Monitoring Alert Coverage**: Projects running Cloud SQL, GKE or load balancers without an **enabled alert policy** about them, plus quota *(v18; Investigation Recommended)*. The match is on what Cloud Monitoring filters say (`cloudsql_database`, `k8s_`, `_lb_rule`, PromQL for GKE, `serviceruntime.googleapis.com/quota`) across every kind of condition — threshold, absence, log match, MQL, PromQL, SQL. Policies kept in a metrics scoping project are not seen.
* **Audit Log Pipeline** *(v18.9)*: Whether the scanned resource's own customer log sinks — the organization's in an organization scan, a folder's or a project's otherwise (`_Required` and `_Default` left out, as Organization Log Sink leaves them) — export the audit trail **completely and durably**. *Organization Log Sink* asks whether an aggregated audit export exists (CIS 2.2); this record asks what it is worth: a filter that names audit logs but admits only some of `activity`, `system_event`, `data_access`, `policy`, or an exclusion that drops audit entries (*Investigation*, with the `--log-filter` line); a folder sink without `--include-children`; a **log-bucket destination kept under 365 days** (*Investigation*) or **unlocked** (Informational — a lock is irreversible, the row says so); a destination that is **gone or not active**, a **writer identity without the destination role** (the IAM-policy search on the destination, its project by ID or number, or a folder or organization above; a project's sink into its own bucket needs none) or **export errors in the last week** (`logging.googleapis.com/exports/error_count`; for organization and folder sinks the metric is tried in the project CloudGauge runs in and skipped quietly when it is not there) — **Action Required**; a destination **in a project outside the scanned scope** is Informational: its retention and the writer's grant cannot be verified from inside. A scope with no customer sink writes one Informational note.
* **Project Log Routing** *(v18.9)*: Per project, the `_Default` sink **disabled, or excluding everything**, with no other sink into a log bucket — the project's logs are discarded as they arrive (**Action Required**); **Data Access audit logs** effective for the project (its own or the organization's configuration) while the `_Default` view of the `_Default` bucket no longer excludes them, so everyone with `roles/logging.viewer` reads who accessed what (Informational, with the view's filter); the `_Default` bucket **without Log Analytics** (Informational — the upgrade is free and irreversible).
* **Alert Notification Channels** *(v18.9)*: Per project, whether the alert policies reach anybody — *Monitoring Alert Coverage* says whether a project has policies at all; this record judges the ones it has: an enabled policy with **no notification channel**, or whose channels are all **disabled, unverified** (`verificationStatus` `UNVERIFIED`: the API's word for a channel that does not deliver) or **gone** (*Investigation*); a **Pub/Sub channel** whose topic is not in the inventory (**Action Required**) or on which the project's Monitoring notification agent (`service-<number>@gcp-sa-monitoring-notification.iam.gserviceaccount.com`) holds no publisher role — undeliverable (*Investigation*; the topic and the grant come from the inventory and the IAM-policy search, no Pub/Sub API call); a policy with an **MQL condition** (Informational — MQL is deprecated in favour of PromQL). Channels are read only in projects whose policies name one.
* **GKE Observability** *(v18.2)*: The metrics side of every cluster — **system metrics off** (no node, pod or container metrics reach Cloud Monitoring; CIS GKE 5.7.1) is **Action Required**; **control-plane metrics** (API server, scheduler, controller manager — free of charge, the first thing an upgrade incident needs) off, **Managed Service for Prometheus** off and, on Standard clusters, **NodeLocal DNSCache** off (Autopilot's own default; container DNS failures are a recurring case) are *Investigation Recommended*, each with the `--monitoring=` / `--enable-managed-prometheus` / `--update-addons` line that keeps what is already on.
* **VPC Flow Logs** *(v18.3, Investigation Recommended)*: Every VM subnet (`PRIVATE` purpose; proxy-only, Private Service Connect, NAT and GKE control-plane subnets exempt) without flow logs (CIS 3.8), with a cost-aware fix (0.5 sampling, 5-second aggregation, all metadata).
* **Network Analyzer**: Network Analyzer's insights — VPC and GKE IP utilization, connectivity, load balancer health, dynamic routes, Cloud SQL connectivity, GKE service accounts — asked at `global` and the active regions, each row with its **severity** *(v18)*: Critical and High are **Action Required**, Medium *Investigation Recommended*, Low *Informational*; an insight type with nothing to say writes its all-clear row.
* **Standalone VMs**: Lists running VMs not managed by a Managed Instance Group (MIG). *Informational* since v18: a standalone VM is a design choice (a bastion, a licence-bound database), so the list is for review, outside the score.
* **Quota Utilization**: Identifies any regional compute quota — and, since v18.1, any project-global one (`FIREWALLS`, `NETWORKS`, `ROUTES`, `IMAGES`, `SNAPSHOTS`, …; region *global*) — over 80% utilization — *Investigation Recommended* from 80 %, *Action Required* from 95 % (v17) — each row naming the quota's family (*Accelerator* for GPU and TPU quotas, *Compute* otherwise) and the headroom left. `COMMITTED_*` quotas are not counted *(v18)*: the commitments consume them by construction.
* **Quota Increase Recommendations** *(v17)*: The quota increases Active Assist's quota recommender suggests, per project: the service, the quota and its current limit, with the recommender's reason.
* **Recent Changes** *(briefing)*: The Recommender's active recent-change insights for each project, and for the organization in an organization scan. *Informational*, with a note when there were none.
* **Platform Footprint** *(v19.1, briefing)*: What runs where, on one page — one all-types search of the Asset Inventory under the scope (names, types, locations, projects; 1,908 assets in 2 s on the reference organization), one content search for the resources whose version matters (GKE clusters: version, channel, Autopilot or Standard, nodes; Cloud SQL: engine and tier; VMs: machine family and state; AlloyDB, Spanner, Memorystore, Bigtable) and the enabled-service assets. The lines, in the Spend Briefing's shape: the **projects**, the **regions** (count and leading families per location), the **enabled APIs** (per project; on everywhere; on in one project only), then one line per product family — Compute Engine, GKE, Cloud Run, Databases, Storage, BigQuery, data processing and messaging, Vertex AI, Networking, identity and secrets, registries and build, Operations — each counted by its own kind first (*7 services, 232 resources*), one for the **Kubernetes objects** GKE indexes (RBAC, workloads, namespaces — 461 on the reference organization) and *Other* for the rest, every line with the `gcloud asset search-all-resources` that lists it. *Informational*, outside the score: nothing here is a verdict. A folder or project scan reads its own subtree.
* **Support Cases** *(v19.2, briefing)*: The open **support cases** under the scope on one page, from the Cloud Support API (`cases.search`, `state=OPEN` — an organization's search returns its own and its projects' cases; a folder scan keeps the folder's projects): seven fixed lines — **open cases** by priority and the oldest, **with Google Support**, **waiting on you** (`ACTION_REQUIRED`, days since the last update), **solution provided** (confirm or reopen before it auto-closes), **escalated**, **by project**, **by product** — the same seven whether there are none or five hundred. Titles and metadata only; a case's description is never read into the report. Every line's Fix is the authenticated read that reproduces it (there is no `gcloud support cases` yet). *Informational*, outside the score. **No new role**: `roles/iam.securityReviewer` already carries `cloudsupport.techCases.list`; the host project needs `cloudsupport.googleapis.com` enabled (`tools/deploy.sh` and Terraform do). Whatever is missing — the API disabled, the permission absent, another refusal — **both support records are still written, Informational, with the exact command that configures them**; the layout never shifts. The support tier is not readable: an organization on Basic support has no cases and reads the same as one with none open.
* **Case Hygiene** *(v19.2)*: From the same search, the open cases that need **your** attention, one row per case: `ACTION_REQUIRED` with no update for more than **3 days** (Google Support waits for your answer) and cases open **beyond the expectation of their priority** — P0 1 day, P1 7, P2 30, P3 60, P4 90 — are *Investigation Recommended*; `SOLUTION_PROVIDED` for more than **7 days** and escalated cases are Informational notes. Cases with nothing flagged: *Compliant*. **No open case at all: Informational** — nothing was judged, and the record says why (none open, or Basic support), so the score is never moved by a tier or a missing API.
* **Bucket Logging** *(v19.3)*: Whether anyone could tell who read or wrote a bucket's objects — two facts, not one: the bucket's legacy **usage logging** (`logging.logBucket`, the only fact Security Health Analytics' `BUCKET_LOGGING_DISABLED` reads) and the **Data Access audit logs** for Cloud Storage (`DATA_READ` and `DATA_WRITE`, `storage.googleapis.com` or `allServices`) effective at the project — set on it or inherited from a folder or the organization. One row per project with buckets: neither → *Investigation Recommended* (no record of who read what; the fix is the audit configuration, or `--log-bucket` per bucket); usage logging absent but Data Access logs on → Informational (covered by the modern path; the row says what SHA's detector misses); every bucket logged → no row. Three inventory listings (buckets, projects, the IAM policies of the containers under and above the scope); scope-level.
* **Unattended Projects** *(organization scans)*: Projects the Recommender reports as unattended (low utilization), by project ID — *Investigation Recommended* since v18 (a hygiene prompt). A listing the scanner cannot read is an *Error* row, not a finding.

*Firewall Complexity* (a project with more than 150 VPC firewall rules) was retired in v18.1: a rule count is not a posture signal. Firewall policies and rule quality belong to the network release of the roadmap; the Changes card of the first scan after the upgrade reads *No longer checked*.

## AI-Powered Insights (Gemini)

* **Executive Summary & Remediation Suggestions**: Generated on demand from the report using Gemini on Vertex AI (via the `google-genai` SDK). The executive summary is generated and read on the report's **Scorecard** page, written for the people who will not open the category pages; remediation lives on the Overview and follows one rule: a check that knows its fix shows it under the finding itself; **Draft fixes** fills in the findings that have none, and marks what it adds as *AI-generated*. Every fix block, built-in or drafted, has a **Copy** button.
* **Automatic model selection**: By default (`GEMINI_MODEL=auto`) CloudGauge uses the newest stable Gemini Flash model available to your project, so it keeps working when older models are retired. Pin a specific model with the `GEMINI_MODEL` environment variable (see [Configuration Reference](stability.md#configuration-reference)).
